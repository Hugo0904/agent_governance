# 長期 Markdown 文件撰寫規則

本文件用於規範長期保存、會被重複導讀的 md 文件怎麼寫，避免把單次對話、敏感資訊或無法泛化的例子沉澱成長期規則。

## 適用範圍
- `agent_governance/agent_docs/*.md`
- `agent_governance/agents/*.md`
- 專案內會被長期引用的規則文件

## 不適用範圍
- task / progress 這類為了交接而保留上下文的任務紀錄
- feature 專屬的操作腳本或 scenario 文件

## 原則
- 先抽象，再落文件：
  若指正或需求來自單次案例，先轉成可重用的通用規則，再寫進長期 md。
- 不寫入敏感資訊：
  token、密碼、私鑰、帳號、webhook、內網位址、真實憑證等資訊不可寫入 md。
- 不寫入一次性特殊名稱：
  若文件目的不是定義某個具名實體本身，避免把單次對話中的具體廠商名、內部代稱、客戶名、票號、案例名直接寫進長期規則。
- 使用中性占位詞：
  需要舉例時，優先使用 `<vendor>`、`<service>`、`<project>`、`<language>`、`<module>` 這類可替換占位詞。
- 只保留規則必要語意：
  文案應描述「什麼情況不能怎麼寫、應改寫成什麼方向」，不要保留與規則無關的案例細節。
- 無法泛化就不要沉澱：
  若內容仍依賴當次任務、當次對話或未確認背景，只記在 task / progress，不寫進長期 md。

## 文件分層與索引（強制）
- `AGENTS.md` 只作為第一層入口：
  只放跨主題的高層載入判斷、主題分流與少量 singleton 規則；不要把已經有父層索引的 leaf 文件全部平鋪進去。
- 一個主題若會持續擴充成多份長期 md，應建立該主題自己的 `README.md` 作為第二層索引。
- 第二層索引負責回答：
  「什麼情況要往下讀哪一份子文件」。
- leaf 文件負責回答：
  「這個主題本身的具體規則是什麼」；不要再重複承擔全域路由角色。
- 同一份 leaf 文件應盡量只掛在一個直屬父層索引下，避免同時出現在 `AGENTS.md`、父層 README、兄弟 README，造成重複入口與維護漂移。
- 若既有父層索引已存在，新增 leaf 時優先掛回該父層；不要直接再往 `AGENTS.md` 增加一條。
- 若某主題第一次從 singleton 成長為 family，應先補父層索引，再決定 leaf 如何分拆。
- 建議採用樹狀關係，例如：
  `AGENTS.md` -> `agent_docs/languages/README.md` -> `php.md`

## 改寫方向
- 由具體名稱改成中性類別詞。
- 由單次案例改成可驗證的條件句。
- 由口語提醒改成 reviewer 可檢查的規則句。

## 自我檢查
- 拿掉具體名稱後，規則是否仍成立。
- 換到另一個專案後，句子是否仍可重用。
- reviewer 是否能只看文件就知道該怎麼檢查。
- `AGENTS.md` 是否只保留第一層入口，而不是把子節點與孫節點全部平鋪。
- 若本次新增的是某個 family 的 leaf，是否已優先更新其父層 README，而不是直接把 leaf 掛回 root。
