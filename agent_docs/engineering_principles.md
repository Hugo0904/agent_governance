# 跨專案工程原則

本文件只存放跨專案通用的工程觀念，不存放任何單一專案的業務真相或框架特例。

## 使用時機
- 當需求在討論跨專案工程觀念，例如 OOP、分層、邊界、重構方式、如何降低 code review 成本。
- 或 `correction_intake.md` 已判定本次指正屬於 `workspace_principle`。

## 原則
- 分層邊界要明確：
  規則應描述哪一層負責流程控制、哪一層負責資料整理、哪一層負責核心邏輯，不用空泛的「要更 OOP」帶過。
- 表現層與核心邏輯分離：
  翻譯字串、畫面文案、展示格式應留在 entry / presentation 層；核心邏輯優先回傳資料、狀態或可轉譯的訊息鍵。
- 依既有架構優先：
  修改前先遵循目標專案既有模式，不憑個人偏好引入新抽象或高版本寫法。
- 資料模型優先於流程特判：
  若某個規則屬於可持久化的業務事實，優先思考由資料表欄位或明確模型承接，而不是把判斷寫死在流程分支、remark key、transport source 或 UI 狀態上。
- 避免用傳遞載具代表業務語意：
  例如 `mail_parcel`、排程、API 入口等只代表交付方式，不應直接拿來當核心商業規則的判斷旗標；業務來源應有自己的資料語意。
- live data 相容性要前置評估：
  面對正式環境已在運行的資料，重構提案需同步思考 migration、backfill、相容讀法與切換順序；若存在更乾淨的長期方案，應主動提出而不是只做最短 patch。
- 規則要可驗證：
  優先寫成 reviewer 能檢查的句子，例如「不要把 Request 傳進 service」而不是「要注意分層」。
- review feedback 要升級：
  重複出現的 review 意見，不應永久停留在口頭提醒，應逐步升級成 md、checklist 或 test。
- 未確認不硬寫：
  若缺乏足夠上下文，先保留待確認，不把猜測沉澱成通用原則。

## 與專案規則的邊界
- 語言本身的語意、語法限制、標準行為或命名慣例：
  移到 `agent_docs/languages/*.md`。
- 長期治理 md 的寫法與抽象方式：
  以 `markdown_authoring_rules.md` 為準。
- 單一專案的 framework 版本限制、資料表真相、功能語意：
  不寫在這裡，應回到專案自身規則。
- 只有跨專案都成立，且未綁定特定業務實作的內容：
  才寫在這裡。
