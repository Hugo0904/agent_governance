# Task Intake 流程規範

## 1. 目的與邊界（強制）
- 本流程用於「先理解任務、再進入實作」的情境。
- `progress` 機制維持原規範，完全不被本流程取代或覆蓋。
- 本流程只定義任務文件整理與確認，不直接修改業務程式碼。

## 2. 觸發方式（強制）
- 當輸入命中以下語意時，進入 Task Intake：
  - `我要執行任務 {檔名}`
  - `我要執行任務 {/path/to/file.md}`
  - `/new {檔名或路徑}`（若入口有提供）
  - `codex` 內明確要求「先導讀任務檔並討論」

## 3. 任務檔路徑解析（強制）
1. 若使用者提供絕對路徑：直接使用該路徑。
2. 若只提供檔名或相對路徑：優先尋找宿主解析出的 workspace `tasks/`。
3. 若宿主未提供 workspace root：停止路徑推測並要求宿主或使用者補充。
4. 若仍找不到：回覆候選檔案清單並要求使用者確認，不可直接猜測。
5. 所有路徑必須在宿主提供的允許根目錄範圍內。

## 4. 標準流程（強制）
1. Intake（導讀）
- AI 先讀任務檔，回覆「理解摘要 + 待確認問題」。
- AI 讀完任務檔後，必須先做「任務內容判定」：依整體語意、涉及系統、參考文件、資料流與操作對象，判斷是否需要參考特定專業代理規範。
- 任務內容判定不得只依賴使用者口語中的單一句型，也不得只靠單一關鍵字或固定廠商代號硬判。
- 若內容明顯涉及特定專業領域，可在導讀階段同步說明「將參考對應代理規範」；例如支付/金流整合可參考 `agent_governance/agents/payment-engineer.md`。
- 若 AI 已有初步理解，可同步說明「目前理解的需求、預計會動到的範圍、下一步準備如何分析」。
- 在使用者明確確認前，不得直接進入實作或修改業務程式碼。

2. Clarify（澄清）
- 使用者補充備註後，AI 更新理解內容。
- AI 可一邊分析程式碼、一邊與使用者商討，但每一輪都應明確回覆：
  - 對原始任務的當下理解
  - 目前觀察到會受影響的程式範圍
  - 預計執行步驟或修改方向
- 若任務內容仍不明確，必須持續商討與確認，不得自行補完需求後直接開做。
- 若任務可能同時落在多個專業領域，或判定信號不足，必須先明確詢問使用者，再決定要套用哪一份專業代理規範。
- 直到使用者明確確認為止，不得視為完成。
- 只有在使用者明確回覆「確認 / 開始做 / 照這樣執行」後，才可進入實作。

3. Confirm（定稿）
- AI 將內容整理進任務文件契約（見 `task_document_contract.md`）。
- 原始任務內容必須保留且不可改寫（Immutable）。

4. Checklist（追蹤）
- 每完成一項已確認工作，更新該任務檔的 checklist 勾選狀態。
- checklist 只紀錄「需求完成度」，不取代 `progress` 執行足跡。

## 5. 寫入規則（強制）
- 優先在同一份任務檔完成四大區塊，不另建影子格式。
- 若原檔尚未有契約結構，可自動升級為契約格式；但原始內容必須完整保留到第 1 區塊。
- 不得刪除使用者已確認的需求內容；若需變更，必須新增「修訂註記」。

## 6. 交接規則（強制）
- 任務檔需可直接交給第三方或其他 AI 接手。
- 交接時至少能看懂：
  1. 原始需求
  2. 已確認的詳細規格
  3. 目前完成度（checklist）
  4. 下一步建議

## 7. 完成判定（強制）
- 以下條件全滿足才可標記完成：
  - 使用者確認「AI 整理內容」正確
  - checklist 已更新到最新狀態
  - 任務檔具備可交接資訊
