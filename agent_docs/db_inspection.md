# DB 檢查流程

本文件只定義「AI 何時可以主動查看本地資料庫、查看前後應遵守什麼規則」，不定義任何單一專案的資料表真相。

## 目的
- 讓 AI 在資料導向問題中，不只看 code，必要時可主動做只讀 DB 驗證。
- 降低因猜錯既有資料狀態、報表來源、權限層級或歷史資料分佈而造成的反覆 code review。
- 避免把 DB 檢查變成每次開發都固定執行的高成本流程。

## 啟用前提（強制）
- 使用者已明確允許此 workspace / 專案可在開發過程中主動查看本地 DB。
- 目標專案自身規則沒有禁止此行為。
- 僅限只讀檢查；若需求涉及修資料、補資料、刪資料，必須先停下來說明。

## 何時應主動查看 DB
- 報表數字、彙總結果、名單篩選與 code 推論不一致。
- 業務語意是否成立，取決於既有資料狀態，而不是只看 controller / service 命名。
- migration、歷史資料相容性、既有資料分佈，會直接影響這次修改是否安全。
- 層級、權限、優惠參與、支付狀態等問題，本質上要靠資料驗證 source of truth。
- 專案規則已要求此類功能修改需先確認資料表或樣本資料。

## 何時不應主動查看 DB
- 純 UI、文案、樣式調整。
- 單純 framework 相容性、語法錯誤、命名或重構問題。
- 只靠 code / migration / 測試就能確認的問題。
- 尚未確認查詢目標與目的，容易變成無邊界亂查。

## 檢查順序（強制）
1. 先看專案規則與既有 code。
2. 再看 `config/database.php`、migration、model / querent / repository 等結構。
3. 仍不足以確認，且屬於資料導向問題時，才做最小範圍的只讀 DB 查詢。

## 查詢邊界（強制）
- 允許：`SELECT`、`SHOW`、`DESCRIBE`、`EXPLAIN` 等只讀查詢。
- 禁止：`INSERT`、`UPDATE`、`DELETE`、`ALTER`、`DROP`、`TRUNCATE`、執行 migration、seed、修資料腳本。
- 優先使用最小範圍條件，避免整表掃描或無限制匯出。
- 不可回傳、記錄或複製敏感資料；回覆只摘要必要結果。

## Docker / 本機資訊
- 若專案 DB 透過 Docker 提供，應先依本工作區文件或本機覆寫文件找到容器、DB 類型與安全的只讀指令。
- 不在 git 版控文件內寫死帳號、密碼、token。
- 若本機命令尚未被允許，需依執行環境的批准流程處理，不可自行繞過。

## 與專案文件的邊界
- 本文件只定義「何時查、怎麼查、查到哪裡為止」。
- 本機 / Docker 存取方式屬於工作區擁有者的操作規則，應放在宿主整合層或本機覆寫，不應直接寫進目標專案 repo。
- 單一專案查哪些 table、哪些欄位是 source of truth、有哪些常見誤判：
  只有在確定屬於團隊共享知識時，才應寫在該專案自己的文件。
